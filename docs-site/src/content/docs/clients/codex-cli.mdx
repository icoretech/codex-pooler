title: Codex CLI and Codex Desktop
description: Configure Codex CLI and Codex Desktop for Codex Pooler's authenticated gemma3 backend façade.

Codex CLI and Codex Desktop should use the Codex backend compatibility route. The client runs its normal local agent loop, tools, sandbox, session storage, compaction, and resume behavior while the gateway exposes one public model, `gemma3`.

Use `/backend-api/codex`, not the SDK `/v1` base URL.

## Configuration

Put provider settings in the user-level `CODEX_HOME/config.toml`. If `CODEX_HOME` is unset, Codex normally uses `$HOME/.codex`.

```toml
model = "gemma3"
model_provider = "codex-pooler"
model_reasoning_effort = "max"

[model_providers.codex-pooler]
name = "OpenAI"
base_url = "https://codex-pooler.example.com/backend-api/codex"
env_key = "CODEX_POOLER_API_KEY"
wire_api = "responses"
supports_websockets = true
requires_openai_auth = false
```

For local setup, change `base_url` to `http://localhost:4000/backend-api/codex`.

Keep `name = "OpenAI"` exactly so Codex enables its OpenAI-family Responses behavior. `requires_openai_auth = false` makes this a gateway-only provider: the Pool API key authenticates model requests and no direct account sign-in is required for the provider.

Export the Pool key separately:

```bash
export CODEX_POOLER_API_KEY="<pool-api-key>"
```

Do not paste the key into `config.toml`, and never put an upstream account credential on the Codex client.

## Run

```bash
codex -m gemma3
```

For a noninteractive check:

```bash
codex exec -m gemma3 \
  'Inspect this repository and report the test command.'
```

The client setting keeps the local UI and session metadata on `gemma3`. The gateway independently normalizes every request before model validation, so another or missing client model selector cannot alter the fixed routing decision or its fixed reasoning policy.

## Websocket and HTTP/SSE modes

The configuration above enables backend Responses websockets for long-running turns and session locality. To force HTTP/SSE for diagnosis, create a second provider whose block is identical except for:

```toml
supports_websockets = false
```

Both transports use the same Pool API key, model identity, policy, retries, continuity, and accounting. A request may retry only before client-visible output. Once output is visible, the gateway never replays the turn and emits one sanitized terminal failure if the upstream stream breaks.

## What the Codex client sees

Authenticated backend model discovery contains at most one model:

- slug and display name: `gemma3`
- one supported reasoning level: `max`
- provider-neutral capabilities derived from the routable target
- no provider, account, assignment, upstream model, or upstream request identifier

Response envelopes, stream identity fields, errors, and allowed response headers preserve that same public identity. When the fixed target is unavailable or prohibited by Pool API-key policy, discovery is empty and inference fails closed; no other model is advertised or selected.

## Continuity, caching, and compaction

Codex session and conversation headers continue through the existing authenticated continuity path. Prompt-cache identifiers are scoped before they can influence account affinity. These mechanisms prefer a compatible connection or assignment but do not guarantee a cache hit.

Backend compact routes remain available to Codex clients. Request-side compression, when enabled for the Pool, can reduce eligible tool-output payloads before upstream dispatch. Neither feature stores raw prompts or model response bodies in request logs.

## Route boundary

The main Codex routes are:

- `GET /backend-api/codex/models`
- `GET /backend-api/codex/v1/models`
- `POST /backend-api/codex/responses`
- `POST /backend-api/codex/v1/responses`
- matching `GET` Responses websocket routes
- `POST /backend-api/codex/responses/compact`
- `POST /backend-api/codex/v1/responses/compact`
- `POST /backend-api/codex/v1/chat/completions`

Explicit backend file and media bridges are documented in [Runtime Routes](/reference/runtime-routes/). Codex Pooler is not a wildcard proxy for account, identity, analytics, realtime, memory, or other Codex app-server APIs. Features that require those direct account services are outside this provider configuration.

## Robustness boundary

This path preserves the Codex CLI's local agent runtime and uses Codex backend-compatible Responses transports, which is the closest supported integration to direct Codex model traffic. The gateway adds Pool authorization, routing, retries, continuity, accounting, protocol projection, and fault isolation.

It cannot make a pooled, translated hop physically identical to a direct connection. Account capacity, network failures, policy, and gateway deployment health still matter. Use the repository's live-client verification gate after deployment to exercise repo reads, shell tools, edits, tests, interruption/resume, streaming, and long-session traffic through the actual instance.
