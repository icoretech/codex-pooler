---
title: OpenAI-compatible SDKs
description: Configure OpenAI SDK clients for Codex Pooler's authenticated single-model gemma3 façade.
---

Codex Pooler provides bounded OpenAI-compatible routes for SDKs and agent clients. The public catalog contains at most one model, `gemma3`. Client-supplied model and reasoning selectors are normalized before authorization and cannot select another model or reasoning policy.

This is not full OpenAI API parity. Use only the routes documented here.

## Base URL and authentication

```text
Base URL:     https://codex-pooler.example.com/v1
Authorization: Bearer <pool-api-key>
Model:         gemma3
```

For local setup, use `http://localhost:4000/v1`. A Pool API key represents a Pool; never configure an upstream account token in a client.

## Python SDK

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["CODEX_POOLER_API_KEY"],
    base_url="https://codex-pooler.example.com/v1",
)

response = client.responses.create(
    model="gemma3",
    input="Reply with: connected",
)

print(response.output_text)
```

## Node SDK

```js
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.CODEX_POOLER_API_KEY,
  baseURL: "https://codex-pooler.example.com/v1",
});

const response = await client.responses.create({
  model: "gemma3",
  input: "Reply with: connected",
});

console.log(response.output_text);
```

Streaming uses the SDK's normal Responses stream API. Public SSE events, final response envelopes, Chat Completions chunks, and legacy Completions all expose `gemma3` when a model field is present.

## Curl smoke test

```bash
curl -sS https://codex-pooler.example.com/v1/models \
  -H 'Authorization: Bearer <pool-api-key>'
```

An available Pool returns exactly one `data` entry whose `id` is `gemma3`. If the server-owned target is not policy-authorized and routable, the list is empty; Codex Pooler does not advertise a fallback.

```bash
curl -sS https://codex-pooler.example.com/v1/responses \
  -H 'Authorization: Bearer <pool-api-key>' \
  -H 'Content-Type: application/json' \
  -d '{"model":"gemma3","input":"Reply with: connected","stream":false}'
```

## Supported inference and discovery routes

| Route | Support |
| --- | --- |
| `GET /v1/models` | Lists only the routable virtual `gemma3` model |
| `GET /v1/models/gemma3` | Returns the virtual model descriptor |
| `POST /v1/responses` | Collected JSON or Responses SSE; text, supported multimodal input, function tools, and continuity |
| `GET /v1/responses` | Narrow Responses websocket transport, not OpenAI Realtime |
| `POST /v1/chat/completions` | Collected JSON or Chat Completions SSE |
| `POST /v1/completions` | Bounded legacy Completions JSON or SSE |
| `GET /v1/usage` | Pool-key-scoped usage metadata |

The server accepts omitted, `gemma3`, or arbitrary client model selectors on supported inference routes and replaces them with its immutable routing decision. Reasoning selectors are also server-owned. Model-detail path selectors are identity-neutral too: any selector resolves to the same available `gemma3` descriptor instead of discovering another model.

For a `previous_response_id` tool continuation, a native `reasoning` replay item
may include `content` with `reasoning_text` parts. Codex Pooler preserves that
accepted reasoning content for the upstream continuation. Stateless replay drops
reasoning items before dispatch instead.

`GET /v1/models` may include `context_length` for clients that probe OpenAI-compatible model lists, such as Hermes. The official OpenAI SDK request APIs and Vercel AI SDK generation APIs do not expose Codex model-catalog context controls. Use their output-budget fields only when your application needs one: `max_output_tokens` in OpenAI Responses, `max_completion_tokens` in Chat Completions, and `maxOutputTokens` at the Vercel AI SDK layer. Codex Pooler's public `/v1/responses` currently rejects `context_management`, and public `/v1/responses/compact` is routed but unsupported, so do not document SDK-side compaction as a Codex Pooler feature.

## Supported file and media routes

| Route | Support |
| --- | --- |
| `GET /v1/files` | Lists authenticated Pool-owned file metadata |
| `POST /v1/files` | Creates upstream-backed file metadata/upload flow |
| `GET /v1/files/:file_id` | Reads owned file metadata |
| `POST /v1/audio/transcriptions` | Audio transcription compatibility |
| `POST /v1/images/generations` | Image generation compatibility |
| `POST /v1/images/edits` | Image editing compatibility |

Dedicated media endpoints use fixed server-owned media helpers where the reasoning target cannot perform that endpoint. Clients still send only `gemma3` and cannot select or discover those helpers. Raw file, audio, and image bodies are not stored in request logs.

## Tools and structured output

Supported function tools, tool calls/results, JSON object output, and bounded JSON Schema output are translated through the Responses path. Unsupported tool families and ambiguous schemas fail locally instead of being guessed. In particular, OpenAI remote MCP tool definitions are not bridged to Codex Pooler's operator MCP endpoint.

The root `/mcp` endpoint is a separate read-only operator service with a separate operator MCP token. Pool API keys do not authenticate it.

## Cache and continuity behavior

Codex Pooler is not a response cache. It preserves provider-side prompt-cache locality without allowing client identifiers to collide across tenants:

- `prompt_cache_key` is converted to a Pool-and-key-scoped digest before routing or upstream dispatch.
- supported Anthropic-style cache breakpoints use the same scoped cache path after translation.
- session and continuity headers affect routing only through bounded, authenticated continuity handling.
- `previous_response_id` and response item IDs are opaque continuation handles; the gateway does not expose provider/account metadata through them.

Locality can improve the chance of a cache hit but never guarantees one. Normal account eligibility, health, quota, policy, retry, and continuity rules still apply.

## Streaming and errors

Before any visible stream content, a retryable failure can move to another eligible assignment. After visible content has been emitted, the request is never replayed; the stream ends with exactly one protocol-safe terminal error.

Errors use OpenAI-shaped envelopes and sanitized messages. Provider, upstream account, assignment, hidden model, upstream request IDs, and rate-limit headers are not relayed. Clients should treat error codes as open strings and keep a fallback for unknown codes.

## Routed but unsupported endpoints

These exact routes authenticate and return deterministic OpenAI-shaped unsupported errors without model dispatch:

- `POST /v1/responses/compact`
- `GET /v1/files/:file_id/content`, after ownership checks
- `DELETE /v1/files/:file_id`, after ownership checks
- `POST /v1/images/variations`
- `POST /v1/content_provenance_checks`
- `POST /v1/embeddings`
- `POST /v1/batches`
- `POST /v1/moderations`
- `POST /v1/fine_tuning/jobs`
- `GET /v1/responses/:response_id`
- `POST /v1/responses/:response_id/cancel`
- `DELETE /v1/responses/:response_id`

`/v1/realtime` and OpenAI Realtime websocket/session routes are absent. `GET /v1/responses` is only the bounded Responses websocket transport.

## Compatibility boundary

OpenAI Responses, Ollama, and Anthropic Messages are different wire formats. Their adapters share routing policy; they are not token-for-token transformations and do not recreate each vendor's local agent runtime.

Identity projection is structural. Codex Pooler rewrites protocol identity fields and strips unsafe headers and error details, but it does not blindly search or alter user text, assistant prose, filenames, or tool arguments. Applications should never rely on content rewriting as a data-loss-prevention control.
