title: Runtime Routes
description: Exact routes, authentication, identity, caching, streaming, and unsupported boundaries for the gemma3 façade.
---

Codex Pooler presents one authenticated virtual model named `gemma3` through four client protocol families. All supported reasoning requests enter the same Pool routing, quota, health, continuity, retry, and accounting path.

Clients cannot choose the private target, provider, account, assignment, or reasoning policy. The server fixes reasoning work to its private target at `max`; if that target is not both policy-authorized and routable, the request fails closed rather than falling back. Dedicated file and media routes retain their bounded server-owned helpers, which are never client-selectable or advertised.

## Base URLs

| Client | Base URL | Public model |
| --- | --- | --- |
| Ollama clients | `https://codex-pooler.example.com` | `gemma3` |
| OpenAI-compatible SDKs | `https://codex-pooler.example.com/v1` | `gemma3` |
| Claude Code and Anthropic SDKs | `https://codex-pooler.example.com` | `gemma3` |
| Codex CLI and Codex Desktop | `https://codex-pooler.example.com/backend-api/codex` | `gemma3` |

Use `http://localhost:4000` for a local instance. Every runtime family requires a Pool API key. OpenAI, Codex, and Ollama clients send `Authorization: Bearer <pool-api-key>`. Anthropic clients can send `x-api-key: <pool-api-key>` or the bearer header; if both are present, they must match.

The root `/mcp` operator endpoint uses a different operator MCP token. A Pool API key never authenticates MCP, and upstream account credentials never authenticate client routes.

## Identity contract

The public identity is structural and immutable:

- catalog and discovery routes return zero or one model, and its name is `gemma3`
- client model selectors are discarded before target-model validation
- client reasoning, effort, thinking-budget, and equivalent selectors cannot change the fixed `max` policy
- response model fields are projected to `gemma3`
- provider, account, assignment, upstream target, upstream endpoint, request IDs, fingerprints, and provider rate-limit headers are removed at the response boundary
- arbitrary user text, assistant prose, filenames, and tool arguments are not searched and rewritten

The final point matters: identity projection is not a generic content filter. If generated prose contains a model-like or provider-like word because the prompt asks for it, Codex Pooler preserves that application content. Use normal data-loss-prevention controls for content policy.

| Route | Status | Behavior |

### Explicitly routed but unsupported

These routes return deterministic OpenAI-shaped unsupported errors and do not dispatch model work:

- `POST /v1/responses/compact`
- `POST /v1/images/variations`
- `POST /v1/content_provenance_checks`
- `POST /v1/embeddings`
- `POST /v1/batches`
- `POST /v1/moderations`
- `POST /v1/fine_tuning/jobs`
- `GET /v1/responses/:response_id`
- `POST /v1/responses/:response_id/cancel`
- `DELETE /v1/responses/:response_id`

`GET /v1/files/:file_id/content` and `DELETE /v1/files/:file_id` are also unsupported, but perform ownership checks first.

OpenAI Realtime routes under `/v1/realtime` are absent. `GET /v1/responses` is the narrow Responses websocket route only. OpenAI remote MCP tool definitions inside a Responses request are unsupported request shapes and fail before dispatch; they are not bridged to `/mcp`.

## Cache and continuity semantics

Codex Pooler does not store and replay completed responses as a cache. Its cache behavior is routing locality for provider-side prompt caching:

1. client cache/session material is accepted only on documented fields or headers
2. façade-specific values are converted to one-way digests scoped by Pool, Pool API key, source, and target
3. only the scoped value may influence routing or upstream cache identity
4. changing Pool or key creates a different namespace

This applies to OpenAI `prompt_cache_key`, translated Anthropic cache controls, and `x-ollama-session-id`. Raw façade cache/session values are not persisted or forwarded. Existing Codex continuity and opaque response-item handles follow their established bounded continuity paths.

Affinity is a preference, not a guarantee. Eligibility, policy, quota, health, retry state, and assignment availability can move a request. A provider cache hit and cached-token accounting are never promised.

## Retry and stream semantics

All supported inference protocols share one visibility boundary:

- before client-visible output, a retryable failure can move to another eligible assignment
- after client-visible output, the request is never replayed
- an interrupted translated stream emits at most one sanitized terminal in its native protocol
- incomplete source frames and tool arguments are bounded and are not released partially
- a terminal event is unique; later upstream frames are ignored

Ollama uses JSON or NDJSON, Anthropic uses Messages JSON or SSE, OpenAI uses its JSON/SSE/websocket shapes, and Codex backend routes retain their backend-compatible framing. These formats are semantically adapted, not byte-for-byte or token-for-token equivalents.

## Error and header cloaking

Authentication, validation, policy, routing, quota, upstream, timeout, and stream errors use the active protocol's public shape. Server-class errors use fixed safe messages. The boundary strips or replaces:

- private target and provider identifiers
- account, assignment, and upstream labels or IDs
- upstream request IDs and system fingerprints
- raw upstream messages and unsafe error fields
- provider rate-limit and diagnostic headers

Locally generated request correlation can remain local. Codex-only safe continuation/model-catalog headers are allowlisted. No response header is copied merely because an upstream supplied it.

## Operator diagnostics

The client façade and operator evidence have different purposes. Authenticated clients see only `gemma3`. Authorized operators can still diagnose and account for real work through metadata-only request logs, attempts, routing outcomes, target/helper identity, applied reasoning, assignment, status, timings, quota, token counts, cache/compression summaries, and safe error codes.

Operator diagnostics do not retain raw Pool keys, upstream credentials, prompts, completions, file/media bodies, websocket frames, raw provider payloads, or raw façade cache/session values. This separation is required for truthful operations without leaking routing internals to clients.

## Operator MCP

`POST /mcp` is the read-only operator JSON-RPC endpoint. `GET /mcp` is routed but stateless SSE is unavailable, and `OPTIONS /mcp` reports allowed methods.

MCP requires an operator-owned bearer MCP token. It does not accept Pool API keys, browser sessions, cookies, query tokens, invite tokens, upstream tokens, or custom authentication headers. It is metadata inspection only and is never invoked as a model tool by `/v1/responses`.
